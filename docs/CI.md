# Store listing CI

From the kit checkout, run `skills/listing-kit/bin/listing-kit link` and follow its PATH hint.

Run `listing-kit ci init` from the app directory. For a monorepo, pass `--app-root 'apps/my app'`. The generator writes CI files at the Git repository root. Outside Git it uses the app directory. App paths must be literal paths without CI expression or glob characters.

Both providers require `--kit-ref`. Set `KIT_REF` to a released tag or a full commit SHA containing the launcher and the adapters you use.

```sh
listing-kit ci init --provider github --kit-ref "$KIT_REF"
listing-kit ci init --provider gitlab --kit-ref "$KIT_REF"
```

Choose the command for your provider. Review and commit the generated file. GitHub uses `.github/workflows/listing.yml`. GitLab uses `.gitlab-ci.yml` for a new pipeline. If that file already exists, the generator writes `listing-kit.gitlab-ci.yml` and prints a one-line local include. Add it to your existing includes. Review the destination before regenerating it. Use `--force` only to replace a regular file whose first line is `# Generated by listing-kit ci init`. The generator refuses unmarked files, including workflows from older versions, and names the path. Projects with custom GitLab stages must make the `test` and `deploy` stages available or adapt the jobs.

## Validate a listing change

A pull request or merge request that changes files in the resolved listing directories or `.listing-kit/` under the app root triggers validation. The runner checks out the app, clones the kit into temporary storage and installs ImageMagick. It runs `listing-kit validate`, builds a fresh review page, and uploads `listing-review.html` for inspection. A validation failure still fails the job. Validation needs no store secrets. Capture and compose run locally. Commit the resulting listing assets before opening the request.

Both jobs fetch the chosen ref and check that `skills/listing-kit/bin/listing-kit` is executable before adding it to PATH. Run `listing-kit detect` to inspect the Apple and Play paths. Regenerate the workflow and review its filters when those paths change or when upgrading.

## Before you rely on this

Pin the GitLab job image (`ruby:3.3-bookworm`) by digest before release.

## Approve a publish

1. Create two protected environments, `store-listing-apple` and `store-listing-play`. Configure required reviewers and restrict which branches or tags may deploy. Where supported, prevent self-approval. A maintainer must configure protection rules for each environment in the provider settings. Check that your provider plan supports the required approval gate before adding keys. [GitHub deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) and [GitLab deployment approvals](https://docs.gitlab.com/ci/environments/deployment_approvals/).
2. Store `APP_STORE_CONNECT_API_KEY_JSON` only in `store-listing-apple` and `PLAY_SERVICE_ACCOUNT_JSON` only in `store-listing-play`. On GitHub, enter the complete JSON as an environment secret. On GitLab, enter it as a protected **File** variable scoped to the matching environment, with variable expansion disabled. GitLab supplies its temporary file path to the publish job. [GitHub Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets) and [GitLab CI/CD variables](https://docs.gitlab.com/ci/variables/).
3. On GitHub, manually dispatch the workflow on the reviewed ref and choose `apple` or `play`. On GitLab, select the manual job for that store on a protected ref. The environment reviewer should check the commit, review page and workflow before approving the deployment. [GitHub manual workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) and [GitLab protected environments](https://docs.gitlab.com/ci/environments/protected_environments/).

The manual CI job uses fastlane 2.242.0. It copies the selected credential to a private temporary file, exports its path and removes the copy on exit. The job passes `--yes` to record approval. Both store gates are off by default. The gated job does not upload or write `.listing-kit/publish.receipt.json`. Read the job log for the preview and any errors. GitLab treats each manual job as optional, so check its status directly.

Agents must never pass `--yes` or set `LK_PUBLISH_UNVERIFIED`. That variable enables real uploads for maintainers' live tests. Keep it out of CI.

With the adapter, the job reports that publishing to that store is disabled and directs you to the hand-upload folder. A build without the adapter prints `this command is not part of this build of listing-kit` and exits 3.

## Keeping keys away from your agent

An agent with a shell can read any file its user can read. A private file outside the repository and a git-ignored path protect against accidental commits. They still allow an agent running as you to read the file.

For strong protection, keep keys only in the CI secret store. Use a trusted, isolated runner. Restrict who can change the workflow, approve deployments or run jobs that receive secrets. Let the agent write the workflow using secret names. Enter the values yourself in the provider settings. Never give secret values to the agent in chat, a terminal command, an issue or a test fixture.
